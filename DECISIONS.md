# TypeSafe.Sdk — Decisions

Newest first.

## Container registration ships as a separate `TypeSafe.Sdk.DependencyInjection` package
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-25)
- **Context**: `services.AddTypeSafeClient(...)` is how every other .NET API client is registered, but it needs `Microsoft.Extensions.Http` (for `IHttpClientFactory`) and `Microsoft.Extensions.Options.ConfigurationExtensions` (to bind a configuration section). Putting those in `TypeSafe.Sdk` would take the core package from one dependency to three for every consumer, including console apps and libraries that never see a container. The alternatives were a single package with the DI types behind an optional dependency (NuGet has no such thing — a `PackageReference` is transitive either way) and no registration helper at all (leaving every consumer to wire `IHttpClientFactory` and the options pattern by hand, which is the boilerplate the story exists to remove).
- **Decision**: A second project and package, `TypeSafe.Sdk.DependencyInjection` (assembly and package id both `TypeSafe.Sdk.DependencyInjection`, root namespace `TypeSafe.DependencyInjection`, extensions in `Microsoft.Extensions.DependencyInjection` so they appear without a new `using`). Its dependency policy: `TypeSafe.Sdk` at the same version plus exactly the two `Microsoft.Extensions.*` packages the registration needs, and nothing else — notably **not** `Microsoft.Extensions.Http.Resilience`, which the README documents as a handler the consumer adds on the returned `IHttpClientBuilder` if they want it. `TypeSafe.Sdk`'s own dependency list stays exactly `Microsoft.Extensions.Logging.Abstractions`. The two packages version in lockstep: both csproj `<Version>`s and `TypeSafeConstants.Version` must agree (see `scripts/check-version.sh`), both are packed by CI and both are pushed from the same `v*` tag, so the `TypeSafe.Sdk` dependency the DI nuspec carries is always the version released beside it.
- **Consequences**: Core consumers are unaffected — the core nuspec is unchanged. DI consumers take three dependencies instead of one, which is what an application in a container already has. A lockstep version means a DI-only fix still republishes the core package at the new version; that is accepted as the cost of one tag, one release. The version check now covers three files and CI/release each gained a second pack step.

## `AddTypeSafeClient` takes a `Func<TypeSafeClientOptions, TypeSafeClientOptions>`, and binds through an internal settings DTO
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-25)
- **Context**: The conventional shape is `AddX(Action<XOptions> configure)`, but `TypeSafeClientOptions` is a `sealed record` with `init`-only properties (see the records decision below), so there is nothing for an `Action` to mutate. Separately, `IConfiguration.Bind` cannot write `init`-only properties reliably, the options record holds members configuration has no business setting (`HttpClient`, `HttpMessageHandler`, `Logger`, `TimeProvider`), and binding it directly would drag reflection into an `IsAotCompatible` assembly.
- **Decision**: The callback is `Func<TypeSafeClientOptions, TypeSafeClientOptions>?`, so a caller writes `options => options with { DefaultModel = "jev-1" }` — it receives the value built from configuration and the environment and returns the derived one, which keeps `init`-only properties and makes the precedence (configuration, then code) visible in the signature. A callback returning `null` throws `InvalidOperationException`. Binding goes through `internal sealed class TypeSafeClientSettings` (plus `TypeSafeRetrySettings`): a mutable, bindable-typed DTO covering only the configurable subset — `ApiKey`, `BaseUrl`, `DefaultModel`, `Timeout`, `LogLevel`, `DefaultHeaders`, `Retry` — bound with `EnableConfigurationBindingGenerator` so no reflection is used, and mapped onto the options record by `ToOptions()`. Unset properties stay `null` so `TypeSafeClient` still resolves `TYPESAFE_*` and its own defaults, and unset `Retry` keys keep their `RetryPolicy.Default` value. Setting `HttpClient` or `HttpMessageHandler` in the callback throws, pointing the caller at the returned `IHttpClientBuilder`.
- **Consequences**: The registration reads a little differently from `AddHttpClient(o => o.Timeout = ...)`, which is the price of value-typed options; the README's Dependency injection section shows the `with` form first so the shape is not a surprise. The DTO is `internal` (with `InternalsVisibleTo` for its test project), so it is not public API and can gain properties without a breaking change, but a consumer cannot inject `IOptions<TypeSafeClientSettings>` of their own — they use the callback. The settings DTO is a second place to edit when an option becomes configurable; the configuration-section table in the README is the contract it has to match. The named `HttpClient`'s own `Timeout` is set to `InfiniteTimeSpan` so it cannot pre-empt the SDK's per-attempt timeout, which is why `ToOptions()` makes the default `Timeout` explicit rather than leaving it `null`.

## Answers keep wire order (`OrderedDictionary`), and the typed views are extension members
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-20)
- **Context**: `AnswerMapConverter` read the `answers` map into a `Dictionary<string, Answer>`, so enumeration order was hash order: a caller iterating `response.Answers` saw an order unrelated to the one the server wrote, and there was no way to ask for "the first answer". The Python SDK's `dict` and the JavaScript SDK's object both preserve insertion order for free, so the C# port was the odd one out. Separately, `Nouls`, `Choices` and `Scores` were private instance filtering on `SystemOneResponse` only, unavailable on a map of answers held anywhere else.
- **Decision**: The converter builds a `System.Collections.Generic.OrderedDictionary<string, Answer>(StringComparer.Ordinal)` (in-box on net10.0) as it reads, so the map is in wire order. `SystemOneResponse.Answers` keeps its declared type `IReadOnlyDictionary<string, Answer>` — no breaking change to the property or the constructor — but the instance behind it is always that ordered map: the constructor keeps an `OrderedDictionary` it is handed as-is and copies any other map into one, in that map's own enumeration order, so a response assembled in code has index access too. Index access is `public KeyValuePair<string, Answer> GetAt(int index)` on the response (forwarding to `OrderedDictionary.GetAt`), chosen over an `this[int]` indexer because `Answers[name]` already reads by name and a positional indexer beside it would be easy to misread; `public int Count` is the answer count. `Nouls`, `Choices` and `Scores` move to C# 14 extension members on `IReadOnlyDictionary<string, Answer>`, in a new `public static class AnswerDictionaryExtensions`, each filtering into an `OrderedDictionary` so the views keep the order of the map they filtered. `SystemOneResponse` keeps all three as instance properties that forward to the extension and cache the result — an instance member wins the lookup over an extension member, so there is no ambiguity to resolve and `response.Nouls` is still built once.
- **Consequences**: `foreach (var (name, answer) in response.Answers)`, `response.Answers.Keys` and the three typed views are now ordered as the server sent them; nothing that looked up by name changes. `LangVersion` stays `latest` — `extension` blocks compile on the .NET 10 SDK — and no reflection is introduced: the views are a runtime type test, as before. The source-generated context never sees `OrderedDictionary`: `SystemOneBody.Answers` is still an `IReadOnlyDictionary` with `[JsonConverter(typeof(AnswerMapConverter))]`, and the converter's `Write` still takes the interface, so serializing a body built from a plain `Dictionary` works unchanged. The public API snapshot gains `AnswerDictionaryExtensions` (PublicApiGenerator renders both the `extension` block and the lowered `get_Nouls`/`get_Choices`/`get_Scores` statics) plus `SystemOneResponse.Count` and `GetAt`. A caller who wrote `IReadOnlyDictionary<string, Answer> map = …; map.Nouls;` on a map of their own now gets the view for free; a caller who had their own extension method of the same name on that interface would see theirs win or hit an ambiguity, which is the only foreseeable source break. Recorded in the README "Differences" section.
- **Update (2026-09-18, task TSDK-20-7)**: The four positional/named `Choice`/`Score` builders take `params ReadOnlySpan<string>` / `params ReadOnlySpan<Content>` instead of `params T[]` (the span is copied into the dictionary or list the record holds, so nothing is retained; collection expressions, loose arguments and explicit arrays all still bind, and the only behaviour change is that an explicit `null` array is now an empty span rather than an `ArgumentNullException`), and the cached `Nouls`/`Choices`/`Scores` properties use the C# 14 `field` keyword with `[field: MaybeNull]` in place of three backing fields. `LangVersion` stays `latest` — both compile on the .NET 10 SDK — and the API snapshot records the four signatures as `[ParamCollection] [ScopedRef] System.ReadOnlySpan<…>`.

## `TypeSafeClientOptions` and `RequestOptions` are sealed records
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-20)
- **Context**: Both option types were already `sealed class`es with `{ get; init; }` properties, while their neighbours — `RetryPolicy`, `Usage`, `ModelMetadata`, the question and answer types — are records. Deriving a variant meant retyping every property, and the README told callers to write `client.Retry with { ... }` for the policy while the options beside it had no `with` at all.
- **Decision**: Declare both as `public sealed record` with the same nominal (non-positional) `{ get; init; }` properties and defaults, `TimeProvider = TimeProvider.System` included. No positional parameters, so no `Deconstruct` and no constructor change. Option resolution (code > environment > defaults) and validation stay in `TypeSafeClient`'s constructor, untouched. `TypeSafeClientOptions.ToString()` is declared explicitly instead of letting the compiler synthesize it, printing `ApiKey = [redacted]` and omitting `DefaultHeaders`, `HttpClient`, `HttpMessageHandler`, `Logger` and `TimeProvider`.
- **Consequences**: Callers gain `with` and value equality on options; a logged or interpolated `TypeSafeClientOptions` cannot leak the API key or a credential-bearing default header, which the synthesized record `ToString` would have printed. Equality is shallow over reference-typed members — `HttpClient`, `Logger`, `TimeProvider`, and the `DefaultHeaders` / `Headers` collections compare by reference, so two option sets carrying equal-but-distinct header dictionaries are not equal. That is accepted: these are identity-like dependencies, not values, and the client copies headers at construction anyway. The public API snapshot gains `: System.IEquatable<T>` on both types and `public override string ToString()` on `TypeSafeClientOptions`; the synthesized `Equals`/`GetHashCode`/`<Clone>$`/`EqualityContract` and the private copy constructor are compiler-generated and do not appear. Both types were already `sealed`, so nothing could have derived from them.

## The package is published to nuget.org from `v*` tags
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-22)
- **Context**: Distribution was source-only — a consumer had to clone the repo and reference `src/TypeSafe.Sdk/TypeSafe.Sdk.csproj`. Story TSDK-22 asks for `dotnet add package`, which needs a registry, a credential and a trigger. The alternatives considered were GitHub Packages (free and already authenticated by `GITHUB_TOKEN`, but consumers must add a feed and authenticate even for a public package) and a manual `dotnet nuget push` from a workstation (no CI secret, but no reproducible build and no guard against pushing an untested or mistagged version).
- **Decision**: nuget.org is the registry (`https://api.nuget.org/v3/index.json`), package id `TypeSafe.Sdk`, so `dotnet add package TypeSafe.Sdk` works against the default feed with no configuration. Publishing is tag-driven: `.github/workflows/release.yml` triggers on a pushed tag matching `v*` only, and pushes with `--api-key` from the repository secret `NUGET_API_KEY` (an nuget.org key scoped to push `TypeSafe.Sdk`; **a human must create it**, and the workflow never echoes it). Before anything is packed the workflow derives `VERSION=${GITHUB_REF_NAME#v}` and runs `scripts/check-version.sh "$VERSION"`, which fails unless the tag, the csproj `<Version>` and `TypeSafeConstants.Version` all agree — the same script CI runs without an argument to keep the two source locations in step. The push includes symbols: `dotnet pack` emits a `.snupkg` (`IncludeSymbols`/`SymbolPackageFormat`) and the SDK's built-in SourceLink (`PublishRepositoryUrl`/`EmbedUntrackedSources`) stamps the pdb, and `dotnet nuget push` sends both packages from the one folder. `--skip-duplicate` makes re-running a tag a no-op.
- **Consequences**: Releasing is a version bump in three files (see the TSDK-25 entry above), a commit, and a `v<version>` tag — there is no manual publish step and no way to publish a version the tag disagrees with. Until someone creates `NUGET_API_KEY` the release job fails at the push step and nothing is published; CI is unaffected, since it packs but never pushes. nuget.org versions are immutable, so a bad release is rolled back by unlisting it and shipping a patch, not by deleting the tag. The README gains an Installation section naming the package id and the registry, and `.project/INFRASTRUCTURE.md` describes the workflow step by step.
- **Update (2026-09-18, story TSDK-25)**: The workflow packs and publishes two packages, `TypeSafe.Sdk` and `TypeSafe.Sdk.DependencyInjection`, from the same tag at the same version. Each has its own pack step writing into `artifacts`; the single `dotnet nuget push artifacts/*.nupkg` glob covers both, so `NUGET_API_KEY` must be scoped to push both ids. `scripts/check-version.sh` now compares three values, the DI csproj `<Version>` included.

## `TypeSafeApiConnectionException` carries the `HttpRequestError`
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-18)
- **Context**: Every transport failure collapsed into one exception with a message, so a caller — or a `RetryWhen` predicate — could not tell a DNS failure from a reset or a TLS error without parsing the message or reaching for `InnerException`. The Python and JavaScript SDKs have no equivalent; their transports do not report one.
- **Decision**: Add `public HttpRequestError? Error { get; }` to `TypeSafeApiConnectionException`, set from a third optional constructor parameter. The transport fills it from `HttpRequestException.HttpRequestError` at both mapping sites (the send and the body read); an `IOException` and `TypeSafeApiTimeoutException` leave it `null`.
- **Consequences**: Additive and C#-side only — messages, wire format and retry defaults are unchanged, and the existing `(message, innerException)` call sites still compile. `RetryWhen = e => e is TypeSafeApiConnectionException { Error: HttpRequestError.NameResolutionError }` now selects a specific transport failure. The property is a .NET-only affordance, so it is listed under README "Differences".

## An enum-typed choice question serializes through the plain `ChoiceQuestion` it projects onto
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-14, task TSDK-14-6)
- **Context**: `Question.Named.Choice<TEnum>(name, instructions)` must return `Named<ChoiceAnswer<TEnum>>`, and `Named<TAnswer>` wraps a `Question<TAnswer>` — so the underlying question has to be a *generic* `Question<ChoiceAnswer<TEnum>>` while still reaching the wire as an ordinary `{"type":"choice", ...}` object. `Question` is polymorphic through `[JsonDerivedType]`, and an open generic cannot be given a discriminator or registered with `TypeSafeJsonContext` (`[JsonSerializable(typeof(ChoiceQuestion<>))]` is not expressible), so `ChoiceQuestion<TEnum>` can never be serialized by the source-generated context itself. Reflection-based serialization is out: the library is built `IsAotCompatible` and must stay warning-free. The same problem appears again on the read side — `SystemOneResponse.Get<TAnswer>` knows only that `TAnswer : Answer`, so it cannot reach `EnumLabels<TEnum>` without `MakeGenericType`/`MakeGenericMethod`, which is exactly the AOT-unsafe reflection the SDK avoids.
- **Decision**: (a) **Writing**: `Question` gains `internal virtual Question ToWire() => this;` and `Question.Serialize` serializes `question.ToWire()` instead of `question`. `public sealed record ChoiceQuestion<TEnum> : Question<ChoiceAnswer<TEnum>>` (where `TEnum : struct, Enum`, its type parameter annotated `[DynamicallyAccessedMembers(PublicFields)]` so the annotation `EnumLabels<TEnum>` requires flows) builds its `Criteria` once in its constructor from `EnumLabels<TEnum>.Entries` — labels in declaration order, each mapped to the member's `[Description]` or to `null` — and overrides `ToWire()` to return `new ChoiceQuestion(Instructions, Criteria)`, the registered non-generic record holding the very same dictionary. The wire JSON is therefore byte-identical to the label-based builder's: `Question.Named.Choice<Tone>("tone", "Tone?")` with `enum Tone { Calm, [Description("upset")] Angry }` writes `{"type":"choice","instructions":"Tone?","criteria":{"calm":null,"angry":"upset"}}`. (b) **Reading**: the private `SystemOneResponse.TryConvert<TAnswer>` hook now takes the `Named<TAnswer>` and delegates to a new `internal virtual bool Question<TAnswer>.TryConvertAnswer(Answer, out TAnswer?, out string? invalidField)` — the question object is the only thing that still knows `TEnum` at runtime, so the mapping is ordinary virtual dispatch and needs no reflection. The base implementation is the runtime type check `Get`/`TryGet` always did; `ChoiceQuestion<TEnum>` overrides it to map the wire `ChoiceAnswer` through `EnumLabels<TEnum>.TryGetMember` into `ChoiceAnswer<TEnum>(TEnum Choice, double Confidence, IReadOnlyDictionary<TEnum, double> Probabilities)` (also not registered with the context: it is only ever built, never parsed). A label the enum does not declare — the selected one or any probability key — sets `invalidField`, and `Get` turns that into `TypeSafeApiResponseValidationException` with `FieldPath` `answers.<name>.choice` or `answers.<name>.probabilities.<label>`, built by a new `internal ApiResponse.Invalid(fieldPath)` that carries the same status code, headers, request ID, endpoint (recovered from `RawHttpResponse.RequestMessage`) and leniently parsed body the transport puts on a body it could not decode. `TryGet` ignores `invalidField` and simply returns `false`.
- **Consequences**: No wire change of any kind, and no new registration in `TypeSafeJsonContext`. `ChoiceQuestion<TEnum>` is a public type whose JSON is produced by another type, so serializing one directly through `System.Text.Json` (outside `Question.Serialize`) would throw on the missing discriminator — the record is documented as never serializing itself. Every `Get` of an enum-typed answer converts afresh, so two reads return equal but distinct `ChoiceAnswer<TEnum>` instances (their `Probabilities` dictionaries are distinct objects, and record equality is reference equality for them). An unmapped label is a *validation* failure rather than a silent drop, which is stricter than the string-typed path, where the caller sees whatever the server sent. The same `ToWire`/`TryConvertAnswer` pair is what a future `ScoreQuestion<TEnum>` (story TSDK-15) should use.
- **Extended to score questions (story TSDK-15, task TSDK-15-5)**: `ScoreQuestion<TEnum>` → `ScoreQuestion(Instructions, criteria)` and `ScoreAnswer<TEnum>` use the very same pair, with two rules of their own, both in the new internal `Rubric` helper beside `EnumLabels<TEnum>` and both reflection-free: (a) a score rubric is a list indexed by score from zero, so the enum's values must be exactly `0..N-1` in declaration order — checked in the constructor with `Convert.ToInt64` over `EnumLabels<TEnum>.Entries`, so an empty, gapped or one-based enum is rejected up front with `TypeSafeException("Enum Urgency must have contiguous values starting at 0 to be used as a score rubric.")`, criteria are each member's `[Description]` falling back to its wire label, and a legend or probability key outside the rubric is invalid response data at `answers.<name>.legend.<key>` / `answers.<name>.probabilities.<key>`; (b) the expected score falls *between* levels, so `ScoreAnswer<TEnum>.Nearest` is `Math.Round(Score, MidpointRounding.AwayFromZero)` clamped to `[0, N-1]` — `1.4` → level 1, `1.5` → level 2, `7.0` and `-1` → the ends — computed and `[JsonIgnore]` like `ChoiceAnswer.Label`.

## Name-first question builders live on `Question.Named`, not as overloads of the positional builders
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-11, task TSDK-11-6)
- **Context**: Story TSDK-11 asks for name-first builders returning `Named<TAnswer>` — the story text spells them `Question.Noul("billing", ...)`, i.e. as overloads sitting beside the existing positional builders `Question.Noul(Content instructions, ...)`, `Question.Choice(Content instructions, params string[] labels)` and `Question.Score(Content instructions, params Content[] criteria)`. `string` converts to `Content` by a *user-defined* implicit conversion, and C# overload resolution prefers the *identity* conversion `string` → `string name`. So every existing all-strings call would silently re-bind to the name-first overload: `Question.Choice("Tone?", "calm", "angry")` would become name `Tone?`, instructions `calm`, one label `angry`, and `Question.Score("Urgency?", "low", "mid", …)` would lose its first rubric entry — no error, just different JSON on the wire. Distinguishing the name by a dedicated parameter type (e.g. a `QuestionName` struct with an implicit conversion from `string`) does not help: `string` → `Content` and `string` → `QuestionName` are both user-defined conversions with no conversion between the target types, so a one-string call becomes *ambiguous* (CS0121) and `Question.Noul("Is it urgent?")` stops compiling.
- **Decision**: The name-first builders live on a nested static class, `public static class Question.Named`: `Question.Named.Noul(name, instructions, whenTrue, whenFalse)`, `Question.Named.Choice(name, instructions, params string[] labels)`, `Question.Named.Choice(name, instructions, IEnumerable<KeyValuePair<string, Content>> criteria)` and `Question.Named.Score(name, instructions, params Content[] criteria)`, each returning `Named<TAnswer>`. Members of two different types never overload each other, so the two families cannot interfere. They return `Named<TAnswer>(string Name, Question<TAnswer> Question)`, a sealed record implementing the non-generic `INamedQuestion { string Name; Question Question; }` (the interface's `Question` is an explicit implementation returning the typed one). An empty or whitespace name throws `TypeSafeException("Question name must not be empty.")`, validated in `Named<TAnswer>` itself — in the primary constructor *and* the `init` accessor, so `named with { Name = "" }` is rejected too. The positional builders on `Question` are untouched and keep serving the dictionary path. The `Questions : Dictionary<string, Question>` collection class is **removed** (task TSDK-11-7): the dictionary-based `SystemOneAsync` overload and `SystemOneRequest` already accept any `IEnumerable<KeyValuePair<string, Question>>`, so callers pass a plain `Dictionary<string, Question>` and the subclass only added a second spelling for one.
- **Consequences**: The story's literal spelling `Question.Noul("billing", …)` is **not** available; the name-first spelling is `Question.Named.Noul("billing", …)`, one segment longer and the closest safe spelling to it. Every existing positional call keeps its meaning byte-for-byte — `QuestionTests`' expected JSON strings pass unchanged, and `NamedQuestionTests.ALoneStringStillMeansInstructionsOnThePositionalBuilders` pins the binding by assigning the results to `NoulQuestion` / `ChoiceQuestion` / `ScoreQuestion` locals, which would not compile if a call had re-bound. `Question.Named` (arity 0) and `Named<TAnswer>` (arity 1) coexist: C# type lookup is by arity, so neither shadows the other. Recorded in the README "Differences" section.

## Unmodelled answers stay in `Answers`, warned about, with their discriminator in the extension data
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-10)
- **Context**: Story TSDK-8 rebuilt reading on `TypeSafeJsonContext` and added `AnswerMapConverter`, which carries an answer whose `type` this SDK version does not model as a bare `Answer`. `SystemOneResponse.FromBody` then warned and *dropped* it, mirroring the Python SDK's skip. Two questions were left open: whether `JsonUnknownDerivedTypeHandling.FallBackToBaseType` makes the converter unnecessary, and whether a dropped answer leaves the caller any way to see what the server sent.
- **Experimental findings**: (a) `FallBackToBaseType` is write-side only. Reading `{"type":"rank","order":["a","b"]}` through `TypeSafeJsonContext.Default.Answer` throws `System.Text.Json.JsonException: Read unrecognized type discriminator id 'rank'. Path: $ | LineNumber: 0 | BytePositionInLine: 23.` with `Path == "$"` — it does not fall back to the base type. Hence the converter. (b) With the converter the discriminator survives: the bare answer's runtime type is exactly `TypeSafe.Answer`, its `Type` property is `""` (the base declares no primitive), and `AdditionalProperties` holds the whole object in wire order — `AdditionalProperties["type"] == "rank"` plus `order`. Because `type` is then ordinary extension data, serializing the bare answer back through the context reproduces `{"type":"rank","order":["a","b"]}` byte for byte (`FallBackToBaseType` writes no discriminator of its own for the base type). Both are asserted in `JsonContextTests` (`AnUnknownDiscriminatorReadStraightThroughTheContextIsARejectedRead`, `AnAnswerTypeTheSdkDoesNotModelDecodesWholeIntoExtensionData`).
- **Decision**: An unmodelled answer is **kept** in `SystemOneResponse.Answers` as a bare `Answer`, not dropped. It is excluded from `Nouls`, `Choices` and `Scores` for free, because those views match on the derived records. `FromBody` still warns once per such answer through the transport logger, at `Warning` level, with the upstream wording preserved verbatim: `Ignoring answer "<name>" with unrecognized type "<type>"`, where `<type>` comes from `AdditionalProperties["type"]` (the empty string if it is absent or not a string). This is a deliberate divergence from the Python SDK, which drops the answer entirely.
- **Consequences**: A caller on an older SDK can inspect a newer server's answer — `response.Answers["mystery"].AdditionalProperties` — instead of only reading it back off `RawHttpResponse`; both routes stay open. `Answers.Count` now counts unmodelled answers, so code that compared it against `Nouls.Count + Choices.Count + Scores.Count` may need updating, and `Answers[name]` can hand back an `Answer` that is none of the three derived types — the typed views remain the safe way to read answers. The message still says "Ignoring", which now means "ignored by the typed views" rather than "discarded": the wording is kept for log parity with the Python and JavaScript SDKs. Recorded in the README "Differences" section. Supersedes the drop described in the TSDK-8 entry below.

## Questions are polymorphic records written by the context; positional parameters are PascalCase
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-9)
- **Context**: `Question` and its three types were classes with hand-written `internal JsonObject ToJson(string name)` methods that built the wire object (and validated it) by hand, the last writer-side reflection-free-but-manual path left after TSDK-8 moved reading onto `TypeSafeJsonContext`.
- **Decision**: `Question` is an abstract `record` with `[JsonPolymorphic(TypeDiscriminatorPropertyName = "type")]` and `[JsonDerivedType]` for `NoulQuestion` `noul`, `ChoiceQuestion` `choice` and `ScoreQuestion` `score`; `NoulCriteria` is a record too. The three question types are positional records (`NoulQuestion(JsonNode? Instructions, NoulCriteria? Criteria)`, `ChoiceQuestion(JsonNode? Instructions, IReadOnlyDictionary<string, JsonNode?> Criteria)`, `ScoreQuestion(JsonNode? Instructions, IReadOnlyList<JsonNode?> Criteria)`), so their constructor parameters are now PascalCase (`instructions` → `Instructions`, `criteria` → `Criteria`) and they gain value equality, `with` and `Deconstruct`. `Question.Type` is `[JsonIgnore]` on the base *and* on every override, because the source generator does not inherit `[JsonIgnore]` from a base declaration; optional fields (`Instructions`, `NoulQuestion.Criteria`, `NoulCriteria.WhenTrue`/`WhenFalse`) carry `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]`, and `[JsonPropertyOrder]` pins `instructions` (1) ahead of `criteria` (2) so the wire order does not depend on where in the hierarchy a property is declared. The single writer-side entry point is `internal static JsonObject Question.Serialize(string name, Question question)`: it validates under the question's name and then calls `JsonSerializer.SerializeToNode(question, TypeSafeJsonContext.Default.Question)`. `RawQuestion` stays outside the polymorphic hierarchy — it is a record deriving from `Question` but is not a `[JsonDerivedType]` — and `Serialize` forwards a deep clone of its own `JsonObject` after `RawQuestion.Validated(name)` runs the same checks as before.
- **Consequences**: Wire output is byte-identical (`QuestionTests`' expected JSON strings pass unchanged) and every validation message is unchanged. Callers who used named arguments on a question constructor (`new NoulQuestion(instructions: x)`) must rename them; the `Question.Noul` / `Choice` / `Score` / `FromJson` builders, which the README and the demo use, keep their lowercase `Content` parameters and are unaffected. The question types are registered in `TypeSafeJsonContext` in the default generation mode rather than `JsonSourceGenerationMode.Serialization`, because the serialization-only fast path does not support `[JsonDerivedType]` (SYSLIB1039); the generated deserialization metadata is unused. The `ToJson` methods and the `Envelope()` helper are deleted; the request envelope is still assembled by hand in `TypeSafeClient.SystemOneAsync` until TSDK-9-6 moves it onto the context.

## `FieldPath` is the reader's JSON path, and unmodelled answer types are read by a converter
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-8)
- **Context**: Transport now deserializes success bodies through the source-generated `TypeSafeJsonContext` instead of the hand-written `Wire` parser, so field paths come from `JsonException.Path` rather than being composed by hand. `System.Text.Json` blames the object it could not construct when a required member is missing, and writes list positions in brackets. Separately, `JsonUnknownDerivedTypeHandling.FallBackToBaseType` only affects serialization: reading an answer whose `type` this SDK version does not model throws.
- **Decision**: `TypeSafeApiResponseValidationException.FieldPath` is `JsonException.Path` with the leading `$.` stripped (`$` alone, and an exception with no path, become `""`). So `answers.tone.confidence` for a wrongly typed value, `answers.tone` for an answer missing `confidence`, `models[0]` for a list position, and `""` for a defect in the whole body (missing top-level member, malformed JSON, empty body). `SystemOneBody.Answers` is read by `AnswerMapConverter`, which peeks each entry's discriminator: a known one is read through the context, an unknown one becomes a bare `Answer` with every field (including `type`) in `AdditionalProperties`, and a missing or non-string `type`, or an entry that is not an object, stays a read error at the same path the `Wire` parser used.
- **Consequences**: Validation messages for a missing member name the containing object rather than the member; the `ResponseTests` expectations were reconciled to the reader's paths. `SystemOneResponse.FromBody` warns about and drops bare answers, so `Answers`, `Nouls`, `Choices` and `Scores` only ever hold modelled answers, exactly as before; the raw payload stays reachable through `RawHttpResponse`. (Superseded in TSDK-10: a bare answer is now kept in `Answers` — see the entry at the top of this file.) The converter composes error paths itself (`$.answers.<name>…`) because a nested `JsonSerializer` call reports paths relative to its own root. With the reader in place the hand-written parser is gone: `Wire`, `ResponseFieldException`, `SystemOneResponse.Parse`, `ListModelsResponse.Parse` and `JsonContent.AsDouble` are deleted (~175 lines). All five were `internal`, so the public surface is unchanged — `SystemOneResponse` and `ListModelsResponse` keep every public member and are now built only through `FromBody`.

## `TypeSafeClientOptions` is init-only
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-3)
- **Context**: The options object had public setters, so it read as live configuration even though `TypeSafeClient` copies every value in its constructor and never looks at the instance again. Mutating options after construction silently did nothing.
- **Decision**: Every `TypeSafeClientOptions` property is `{ get; init; }`, matching `RequestOptions` and `RetryPolicy`. Callers configure the client in an object initializer; there is no post-construction mutation to mislead them.
- **Consequences**: Code that built an options instance and then assigned to it must move the assignments into the initializer. The test helper `Clients.Create` keeps its `o => o.X = ...` ergonomics through a mutable test-only `ClientSetup` holder that is applied in the initializer.

## `ListModelsResponse` is the list; answers gain `Probability` / `Label` aliases
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-3)
- **Context**: `client.Models.ListAsync()` returned a response whose only content was a `Models` property, so every caller wrote `models.Models`. Separately, the earlier "Answer property names mirror the wire format" decision deferred the `Probability` / `Label` aliases.
- **Decision**: `ListModelsResponse` implements `IReadOnlyList<ModelMetadata>` (`Count`, indexer, `GetEnumerator`) over a private backing list, and the `Models` property is removed — one way to reach the models, not two. `NoulAnswer.Probability` and `ChoiceAnswer.Label` are added as get-only computed aliases of `Noul` and `Choice`, marked `[JsonIgnore]` so a future source-generated `JsonSerializerContext` (planned in TSDK-7) cannot leak them onto the wire.
- **Consequences**: C#-side surface changes only; wire parity unchanged. Callers using `response.Models` iterate or index the response itself. The wire names stay primary in the docs, with the aliases documented as conveniences.

## HTTP status codes are exposed as `HttpStatusCode`
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-3)
- **Context**: The port carried the upstream integer `status` through `ApiResponse.Status`, `TypeSafeApiException.Status` and the exception constructors, with `StatusCode` bolted on as a derived enum property.
- **Decision**: `ApiResponse` and `TypeSafeApiException` expose `HttpStatusCode StatusCode` only; the exception constructors and `TypeSafeApiException.FromResponse` take an `HttpStatusCode`. No `int Status` and no obsolete shims — this is the breaking-change release. `RetryPolicy.HttpStatuses` stays `IReadOnlySet<int>` so callers can list codes the enum does not name.
- **Consequences**: A C#-side naming and type change only; exception messages still start with the numeric code, so wire and log parity are unchanged. Callers reading `Status` must switch to `StatusCode` and cast when they want the number.

## `RetryPolicy` retry flags are named as actions
- **Date**: 2026-09-18
- **Status**: Accepted (story TSDK-3)
- **Context**: The port carried the upstream error-type names `ApiConnectionError`, `ApiTimeoutError` and `Predicate`, which read as error objects rather than as the switches they are.
- **Decision**: Rename to `RetryConnectionErrors`, `RetryTimeouts` and `RetryWhen`, per the naming table from the typing review. No obsolete shims — this is the breaking-change release.
- **Consequences**: A C#-side naming change only; the wire format and retry behaviour are unchanged. Callers setting the old names must rename.

## Retarget to net10.0 and adopt C# 14 features
- **Date**: 2026-09-18
- **Status**: Accepted (epic TSDK-1)
- **Context**: .NET 9 (STS) left support in May 2026 and .NET 8 (LTS) leaves in November 2026. The port targets net8.0 and cannot use C# 13/14 or the .NET 9 System.Text.Json features (`AllowOutOfOrderMetadataProperties`, `RespectRequiredConstructorParameters`, `JsonSerializerOptions.Web`).
- **Decision**: Single `net10.0` target; enable `IsAotCompatible`; apply the naming table from the typing review.
- **Consequences**: Drops the `RollForward=Major` workaround. Consumers on .NET 8 cannot use versions after this change.
- **Update (2026-09-18, task TSDK-2-4)**: `<IsAotCompatible>true</IsAotCompatible>` is now set permanently in
  `src/TypeSafe.Sdk/TypeSafe.Sdk.csproj`. It implies `IsTrimmable`, `EnableTrimAnalyzer`, `EnableAotAnalyzer` and
  `EnableSingleFileAnalyzer` (verified with `dotnet msbuild -getProperty:`), so the trim/single-file/AOT analyzers run
  on every build. A full `dotnet build --no-incremental` of the solution reports **0 warnings**: every
  `JsonSerializer` call now goes through `Internal/TypeSafeJsonContext`, and the only members carrying
  `RequiresUnreferencedCode` / `RequiresDynamicCode` are `Content.From(object)`, `Internal.JsonContent.From(object)`
  and the `Internal.JsonContent.SerializerOptions` getter. `PublicSurfaceTests.OnlyTheReflectionConversionRequiresUnreferencedOrDynamicCode`
  asserts that set by reflection, so a new unannotated reflection path fails the suite.
- **Publish check on this machine (2026-09-18)**: `dotnet publish examples/TypeSafe.Sdk.Demo -c Release -r linux-x64
  -p:PublishAot=true` **succeeded end to end** on the first attempt — ILCompiler restored, "Generating native code"
  emitted no IL warnings, and the native binary landed at
  `examples/TypeSafe.Sdk.Demo/bin/Release/net10.0/linux-x64/publish/TypeSafe.Sdk.Demo` (7.1 MB, stripped ELF). No
  `-p:CppCompilerAndLinker=gcc` override was needed (gcc at `/usr/bin/gcc`, no clang installed). The
  toolchain-independent `-p:PublishTrimmed=true --self-contained` publish also ran ILLink to completion with 0
  warnings. The demo uses `Content.From(state, DemoJsonContext.Default.DemoState)`, so it never touches the
  annotated reflection overload; a consumer that does will see `IL2026`/`IL3050` at their own call site by design.

## Replace `object?` inputs with a `Content` value type
- **Date**: 2026-09-18
- **Status**: Accepted (epic TSDK-2)
- **Context**: Builders and `state` accept `object?` and run reflection serialisation with camelCase naming. That is the only untyped, trim-unsafe part of the surface and it renames consumer properties silently.
- **Decision**: `readonly record struct Content(JsonNode? Node)` with implicit conversions from `string`, `JsonObject`, `JsonArray`; `Content.From<T>(T, JsonTypeInfo<T>)` for source-generated callers; the reflection overload kept but annotated `[RequiresUnreferencedCode]` / `[RequiresDynamicCode]`.
- **Consequences**: Breaking change to builder signatures. Anonymous-object callers must use `Content.From(obj)` explicitly.

## Async-only public API
